\section{Conda packages}\label{sec:conda-packages}

The conda packaging format~\cite{conda_software} is general yet powerful.
A conda package is fundamentally a \texttt{zip} compressed archive (\texttt{.conda}) containing two Zstandard compressed \texttt{tar} archives (\texttt{.tar.zst}).
One archive contains relocatable files, platform-specific binaries, and, potentially for Unix-based platforms, symlinks.
The other archive contains metadata that comprehensively describes the package contents, provenance, requirements, and dependencies.
As the conda package format is language agnostic it can be used to effectively package any software as a conda package.
This has allowed for wide support of libraries and tools from Fortran (e.g. \href{https://github.com/conda-forge/lapack-feedstock}{LAPACK}), C++ (e.g. \href{https://github.com/conda-forge/boost-feedstock}{Boost}), CUDA (e.g. \href{https://github.com/conda-forge/cudnn-feedstock}{cuDNN}), Python (e.g. \href{https://github.com/conda-forge/scipy-feedstock}{SciPy}), and other languages used across science such as Rust and Go.
It also allows for software projects that expose interfaces in multiple languages to be packaged in their entirety as a single conda package (e.g. \href{https://github.com/conda-forge/root-feedstock}{ROOT}).

The conda packaging format has benefited from robust standards that are achieved through iterative improvements and hardening through the Conda Enhancement Proposals (CEP) process~\cite{CEPs}.
This has allowed for packaging of a complex software ecosystem to continue without invalidating or breaking existing conda packages.
For example, the conda package format requires that all build tools, linked libraries, and runtime dependencies specified in the package recipe --- that define how a conda package is built, packaged, and tested --- also exist as conda packages.
This bootstrapping system ensures that all dependencies of a package exist in a coherent format that is free of operating-system-level assumptions down to the low-level C library requirements --- which cannot be installed as conda packages themselves.
CEP 30~\cite{CEP30} defines ``virtual packages'' that represent these system-level dependencies, allowing conda packages to declare dependencies on these virtual packages without assuming their installation method.
Similar enhancements have allowed virtual packages for specific hardware features, such as CEP 46~\cite{CEP46} which defines the \texttt{\_\_cuda\_arch} virtual package for CUDA architectures.
This allows for robust definition of hardware acceleration dependencies.
Combined with the work by the NVIDIA open source team to provide the full CUDA stack of tools, from the CUDA compiler \texttt{nvcc} to the high-level development libraries, these standards have allowed for conda packages to be a robust and portable technology for CUDA-enabled software packaging and distribution.

The conda packaging format also allows for the creation of multi-platform packages.
A conda recipe can be built for all defined computing platforms that the underlying software supports without having to duplicate the recipe.
This allows for building conda packages across all computing platform combinations of operating systems and hardware architectures, such as Linux, macOS, and Windows on x86\_64, ARM, and PowerPC architectures (e.g. \texttt{linux-64}, \texttt{osx-arm64}, \texttt{win-arm64}).
Most importantly for the HEP software community, having x86\_64- and AArch64-based multi-platform builds for Linux allows for ensuring robust support and distribution across all computing systems that are available and prioritized in the community, such as for the upcoming HL-LHC era~\cite{CERN-LHCC-2022-005}.
Additionally, the conda packaging format already supports RISC-V architectures (e.g. \texttt{linux-riscv64}), which may be of interest to the HEP community in future experiments.
Beyond computing platforms, the conda packaging format also supports ``build variants'' that allow for creating multiple builds of the same package version with different configuration options, such as ``microarch'' level instructions for enabling Single Instruction, Multiple Data (SIMD) instruction sets and Message Passing Interface (MPI) standard specifications like MPICH and OpenMPI.
Build variants allow for optimizations to be applied throughout entire toolchains that can lead to performance that comes close to machine-level bespoke optimizations while retaining the ability to easily change and reproduce software environments.

Finally, the conda packaging format also allows for multiple rebuilds of a particular package version through including the build number as package metadata (where higher build numbers are preferred by package resolver software).
This allows for long-term support of older releases of software by rebuilding against newer compatible versions of dependencies while maintaining the same package version and source code.
Allowing for multiple package builds to exist simultaneously on a conda package index (a ``conda channel'') combined with a lack of operating-system-specific assumptions and digest-level lockfile tooling~\cite{Feickert:2025qru,fischer2025pixiunifiedsoftwaredevelopment} makes conda packages a compelling technology choice for robust long-term support software distribution and preservation.

\section{Conda-forge}\label{sec:conda-forge}
Building on the standards of the conda packaging format, conda-forge~\cite{conda_forge} is open source community cyberinfrastructure that acts as a ``forge'' for conda packages by providing global build infrastructure and automation systems driven through continuous integration actions on independent software project ``feedstock'' GitHub repositories under the conda-forge GitHub organization (\href{https://github.com/conda-forge/}{https://github.com/conda-forge/}).
The conda-forge community project also includes the \texttt{conda-forge} conda channel, which hosts all of the built package artifacts from the conda-forge build cyberinfrastructure.
Conda-forge also provides ``global pinning'' infrastructure to automatically migrate ABI changes across the entire ecosystem through long-running automated DevOps workflows.
This ensures that all packages on conda-forge are built coherently together and supports building and using all packages built on conda-forge together while minimizing the potential for conflicts.

As of September 2026, conda-forge builds and distributes over 34,000 conda packages which have resulted in over 48 billion package downloads (with over 1.5 billion monthly package downloads)~\cite{conda_forge-website}.
Despite the growing number of packages, as of September 2026, the public \texttt{repodata.json} files on conda-forge report a total size of all packages on conda-forge of around 25.2 TB.\footnote{The storage for the entirety of conda-forge and its bandwidth use is provided as an in-kind donation by Anaconda, Inc.}
The relatively small disk size is due to multiple design decisions in conda-forge Enhancement Proposals (CFEPs)~\cite{CFEPs} but most impactful is the prioritization of dynamic linking of shared libraries in conda-forge conda packages over statically linked libraries.
These choices make it possible for multiple organizations to provide full mirrors of conda-forge at affordable disk cost.
This allows for organization-specific security practices and organization-internal builds to be maintained on specific (and potentially private) conda channels that build on top of the conda-forge mirror.
